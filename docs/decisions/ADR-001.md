# **ADR-001: Event-Sourced Request Status Audit History vs. State Overwriting**

## **1\. Problem**

In an enterprise request tracking platform, requests undergo deterministic state transitions (Submitted → Pending Approval → In Progress → Blocked → Resolved/Declined). The system must provide complete observability and auditability into historical state changes, actor actions, timing metrics, and SLA performance. The core decision is how to record request state updates without creating unnecessary administrative overhead or sacrificing system query performance.

## **2\. Options Considered**

### **Option 1: Overwrite Current Status (In-Place Mutation)**

> * **Description:** Update a single status column in the main requests table whenever a state transition occurs.  
> * **Pros:** Simple schema design and fast single-record queries for current status.  
> * **Cons:** Complete loss of historical state context, transition timestamps, and actor accountability. Violates security and compliance requirements.

### **Option 2: Dual Storage — Mutable Current State \+ Append-Only Audit History Table**

> * **Description:** Maintain current state in the primary requests table for fast queries, while transactionally appending every status transition to an immutable audit\_entries / request\_history event log table.  
> * **Pros:** Provides full historical auditability and SLA metrics while keeping current state queries fast and simple. Ensures low operational complexity for early iterations.  
> * **Cons:** Requires transactional integrity across two table writes during state transitions.

### **Option 3: Full Event Sourcing Architectural Pattern**

> * **Description:** Store all state changes strictly as an append-only stream of domain events and project the current state dynamically at runtime.  
> * **Pros:** Complete historic auditability and infinite replayability.  
> * **Cons:** High initial engineering complexity, heavy infrastructure overhead, and difficult debugging for a v0.1 foundation.

## **3\. Decision**

**We choose Option 2: Mutable Current State \+ Append-Only Audit History Table.**  
Every request state transition will transactionally write to the primary requests record (updating status and updated\_at) and concurrently append an immutable entry to audit\_entries capturing request\_id, previous\_status, new\_status, actor\_id, and timestamp.

## **4\. Consequences**

### **Positive Consequences**

> * **Full Audit Trail:** Complete history of state transitions, timing, and actor attribution is preserved for compliance and SLA tracking.  
> * **High Query Performance:** Active queue dashboards can query the primary requests table directly without complex joins or event fold aggregations.  
> * **Balanced Complexity:** Delivers complete traceability required for v0.1 without introducing the architectural overhead of full Event Sourcing.

### **Negative Consequences & Mitigation**

> * **Storage Growth:** The audit\_entries table will grow rapidly over time.  
>   *Mitigation:* Index (request\_id, created\_at) for fast sequential lookups and consider partitioning or archiving historical logs in future iterations.  
> * **Dual-Write Consistency:** Risk of desynchronization between current state and audit log.  
>   *Mitigation:* Enforce all state transitions inside database transactions or database-level triggers.
